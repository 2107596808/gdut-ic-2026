## 2. 阶段一：能自己玩的版本

### 实现

规则层是**纯函数**，完全不碰 DOM，所以能被 Node 直接调用做自动验收：

| 函数 | 作用 |
| --- | --- |
| `createGrid()` | 生成 16 格的一维棋盘（`0` 表示空） |
| `slideRow(row)` | 把一行左压 + 合并，返回新行与本次得分 |
| `applyMove(grid, dir)` | 四个方向的完整移动，返回新棋盘 / 得分 / 是否真的动了 / 合并位置 |
| `canMove(grid)` | 还有空格或还有相邻同值 → 游戏没结束 |
| `addRandomTile(grid, rand)` | 随机空格落一个方块（90% 是 2，10% 是 4） |

**合并规则**：一行里每个方块每一步只能合并一次。`[2,2,2,2]` 得到 `[4,4]` 而不是 `[8]`，
这条是 2048 最容易写错的地方，所以在验收脚本里专门有断言。

**三项新增功能**（任务书要求三选一，这里三项都做了，按验收标准逐条对照）：

| 新增功能 | 验收标准 | 本项目实现 |
| --- | --- | --- |
| 计分制 | 记录得分/最高分/局数；新一局不清零；有「重置」按钮 | 顶部分数栏 + 右侧状态栏；`localStorage` 持久化；「新一局」只重置当前局；「重置记录」单独清空记录 |
| 主题切换 | ≥2 套配色；一键即时生效；刷新后保留 | 深浅两套配色（CSS 变量 + `data-theme`）；点击立即生效；写入 `localStorage`，刷新恢复；首次打开跟随系统 `prefers-color-scheme` |
| 多局战绩 | 记录最近 10 局；新一局自动追加；可查看完整列表 | 每局结束写入战绩（得分/最大方块/步数/是否 AI 操作）；`pushRecord` 自动截断到 10 条；右侧面板列出完整列表 |

### 验证

```bash
node game/tests/verify_game.mjs          # 自动验收（不需要浏览器）
python game/tests/verify_static.py       # 单文件 / 无外链 / 功能点静态检查
```

`verify_game.mjs` 的做法值得说明：它**不复制一份逻辑来测**，而是用正则把 `index.html` 里的
`<script>` 源码抠出来，配上一套自制的「假 DOM + 假 localStorage」，丢进 Node 的 `vm` 里跑，
再通过 `window.Game2048`（逻辑层）和 `window.__2048__`（UI 桥接层）两个出口做断言。
所以它测的是**真正会跑在你浏览器里的那份代码**。

阶段一相关的断言（共 40 余项，节选）：

- `[2,2,2,2] → [4,4,0,0]` 且只加 8 分（不允许越级合并）
- 四个方向的移动结果都和参考实现逐格一致（随机 10000 次方向对比，零差异）
- 无效移动必须返回 `moved = false`（否则会凭空冒出新方块）
- 连续 40 步移动后，界面显示的分数与规则层累加的分数完全相等
- 新局渲染出 16 个背景格、分数显示同步
- 一键切换主题即时生效，并写入 `localStorage`
- 连开 12 局后战绩只剩最近 10 条，且保留的是最近的（脚本会核对首尾两条的具体分值）
- 「重置记录」后最高分/局数/战绩全部归零
- 键盘、鼠标拖拽两种输入都能操作棋盘

## 3. 阶段二：让 AI 来玩

### 3.1 AI 是怎么做的

**一句话**：AI 用「**角块启发式 + expectimax 搜索**」，评估函数照搬了开源实现
[qpwoeirut/2048-solver](https://github.com/qpwoeirut/2048-solver)（C++）里效果最好的那一套，
搜索部分按 JavaScript 的情况重写。

- **角块启发式（corner heuristic）**：给棋盘四个角各准备一张权重表，
  越靠近角的格子权重越大（10 / 5 / 2 / 1），把每格的「权重 × 方块值」加起来，四个角取最大。
  含义很直白：**把大块堆在角落里、并且沿着某一条边排开**。
- **expectimax**：
  - 我的回合 → 取 `max`（四个方向里挑期望最高的）
  - 随机落子回合 → 取**期望**：对每一个空格，分别按 90% 出 2、10% 出 4 计算加权平均
    （**全宽**遍历，不抽样——抽样会漏掉「棋盘被填满」的风险局面）
- **自适应深度**：棋盘越满、方块种类越多就搜得越深（2 ~ 8 层）。
  局面很空的时候深搜没有意义（主要是运气），局面紧张时才需要多想几步。
- **平局裁决**：期望分相同时先看角块分，再看「蛇形字典序」，保证不会在等价走法之间乱抖。

### 3.2 为什么要用位棋盘

把整个 4×4 棋盘压进**两个 32 位整数**（`lo` 前两行、`hi` 后两行，每格 4 bit 存 `log2(方块值)`，
也就是「等级」，0 表示空格）。这样「移动整块棋盘」就退化成几十次位运算 + 查表，
比数组版快一个数量级——而 AI 的棋力几乎完全取决于**单位时间能搜多少个节点**。

⚠️ 这里踩过两个必须记住的坑（都写在代码注释里了）：

1. **JS 位运算只有 32 位**：`1 << 48` 不会得到一个 64 位数，而是被截断成 `1 << 16`，
   而且**不报错**，只是默默算出错误的棋盘。
2. **不能用 `lo + hi * 2^32` 拼成一个大整数**：64 bit 的棋盘超过 JS 的
   安全整数上限（2⁵³），高位会被悄悄吃掉。需要唯一标识一个局面时只能拼字符串。
3. **置换表的键不要做哈希混合**：这是最后才查出来、也是最贵的一个坑。
   我一开始把 `lo / hi / depth` 用两个 `Math.imul` 做了 avalanche 混合，
   看着很「专业」，结果 CPU profile 显示 `mix32` 占了 **41%** 的时间 —— 它才是全文件
   最大的性能杀手。换成朴素的位拼接（`(lo * 131072 + (hi >>> 15)) * 16 + depth`）之后，
   同样的搜索快 **3.8 倍**（depth=5 从 1032ms 降到 266ms），同样时间预算能多搜 4 倍节点，
   1024 达成率直接从 3/6 变成 6/6。**置换表只需要「不同局面基本不撞」，不需要密码学质量。**

### 3.4 怎么验证的（三类验证）

1. **规则层正确性**：用 `slideRow`（已被单测钉死的参考实现）做基准，
   随机 10000 个局面 × 4 个方向，逐格比对数组层和位棋盘层的移动结果 —— 零差异。
   这条断言是发现「右移查表少做了一次镜像」「shift ≥ 32 被截断」这两个 bug 的关键。
2. **AI 行为**：固定种子跑整局，统计达成率、平均步数、单次决策耗时；
   同一批种子每次结果必须一致（`makeRng` 是 xorshift32），否则说明引入了不确定因素。
3. **界面契约**：静态检查 HTML 里每个 `id` 与 JS 引用对得上、
   没有外链、恰好一个内联 `<script>`；再看键盘/鼠标事件有没有真的绑上。

## 4. 关键提示词与迭代过程

> 任务书要求：「用 AI 做出来非常简单，关键看你怎么设计提示词——先想清楚需求，再一步步让 AI 实现」。
>
> 说明：我确实是**用 AI 工具写这个项目的**，下面记的是每一轮「我想要什么 → 得到什么 → 怎么改」。
> 其中技术细节是我自己读代码、看数据核出来的（第 5 节的「AI 说错但我查证过」就是其中一例）。

### 第 1 轮：把需求说清楚（而不是说“帮我做个 2048”）

**我给 AI 的提示词：**

> 用纯前端单文件（HTML/CSS/JS）做一个 2048，要求：
> 1. 无框架、无外部依赖、双击打开就能玩
> 2. 键盘方向键 + WASD、鼠标拖拽、触屏滑动都能操作
> 3. 界面常显：得分、最高分、步数、最大方块
> 4. 另外加三个功能：计分制（得分/最高分/局数，新局不清零，有重置按钮）、
>    主题切换（深浅两套配色，刷新后保留）、多局战绩（记录最近 10 局）
> 5. **重要**：把纯逻辑（移动、合并、判负）和 DOM 操作分开，逻辑层导出成
>    `window.Game2048`，我要用 Node 直接调它做自动验收；UI 层另外导出 `window.__2048__`
> 6. 注释全部写中文，关键算法要解释“为什么这么写”

**结果**：一次就拿到了结构正确的单文件，逻辑层/UI 层分离也做到了。
**这次成功的经验**：第 5 条是关键——把「我要怎么验收」一起写进提示词，AI 才会把代码切成可测的形状。
后来验收脚本能在 Node 里跑真实代码，就是这一步埋下的。

### 第 2 轮：AI 方向（第一次尝试失败）

**我给 AI 的提示词：**

> 加一个「AI 自动演示」：点一下就不需要任何人工操作，一直玩到合出 1024。
> 用很小的代码量实现就行（贪心 + 评分函数，评分看空格数和可合并对）。

**结果**：AI 能跑，但很快就把棋盘塞满，最高只到 128 左右。
**问题定位（我自己读代码 + 加日志看出来的）**：贪心只看一步，遇到「这一步能合并、但那一步能保命」时
会选前者，于是越玩越乱。
**提示词怎么调整**：不再要求「用很小的代码量」，而是明确要求**搜索**：
「我方回合取 max，随机落子回合对每个空格按 90% 出 2 / 10% 出 4 求期望，也就是 expectimax」。

### 第 3 轮：明确要求参考成熟实现

**我给 AI 的提示词：**

> 参考 https://github.com/qpwoeirut/2048-solver 里效果最好的方案：
> 评估函数用 corner heuristic（四个角各一张 10/5/2/1 权重表，取最大），
> 搜索用 expectimax，深度按局面自适应（越满越深），平局用蛇形字典序裁决。
> **搜索部分要用位棋盘实现**：把 4×4 棋盘压成整数，每格 4 bit 存 log2(方块值)。
> 但注意 JS 的位运算只有 32 位，请把棋盘拆成 lo/hi 两个 32 位整数。

**结果**：结构对了，但棋力反而更差（最高 256）。
**这一步我做的事**：写了个把「位棋盘移动」和「数组层移动」逐格对比的脚本，
一跑就发现两者不一致 —— 于是找到了后续一串 bug。
**提示词怎么调整**：加了硬约束「**每写完一块，必须能用一个纯函数脚本证明它和数组层结果一致**」。
后面每次改 AI，我都先跑这个等价性对比。

### 第 4 轮：靠数据定位，而不是靠继续加要求

**我给 AI 的提示词（第 4 轮起基本不再改需求，改成“这是数据，请解释”）：**

> 现在 5 局固定种子跑下来，最高方块只有 256；同样的评估函数，把深度改成 4/5/6 反而更差。
> 这是不符合常理的（搜得越深不应该越差）。请检查：
> 1. 截断时返回的值会不会污染父层的比较？
> 2. 时间预算是不是被第一个方向吃光了，导致后面方向只搜到一层、和深搜值混在一起比大小？
> 3. 置换表的 key 有没有把深度考虑进去？

**结果**：定位到三个具体缺陷，逐个修掉后棋力从「最高 256」跳到「稳定 1024、偶尔 2048」：

| 缺陷 | 后果 | 修法 |
| --- | --- | --- |
| 四个方向共用一份时间预算 | 第一个方向花光时间，后三个只搜 1 层，等于拿「深搜值」和「静态分」比大小 | 每个方向发等额预算，整层共享 deadline |
| 预算耗尽只是 `return` | 父层循环仍把剩余兄弟节点全部走完，退栈代价 O(剩余节点数)：实测 `timeMs=10` 要跑 648 ms | 预算耗尽处 `break`，退栈回到 O(深度) |
| 被截断的局面也写进置换表 | 残缺值被缓存 → AI 系统性躲开「刚好被截断」的走法，偶发崩盘 | 截断的节点不写缓存；并改成**迭代加深**：只认「四个方向都完整搜完」的那一层 |

**这一轮最大的收获**：AI 提示词里写「请检查 X、Y、Z」比写「再聪明一点」有用得多。
把观察到的异常现象（“搜得更深反而更差”）和可能的机理一起给它，它才能定位到真问题。

### 第 5 轮：交给验收脚本定标准

**我给 AI 的提示词：**

> 把验收脚本补全：固定 10 个种子各跑一整局（全程无人工），统计 1024 达成率、平均得分、
> 平均步数、单次决策耗时，并且**低于 80% 达成率就直接退出码 1**。
> 另外把我的「阶段一三项新增功能」也逐条写成断言（计分制 / 主题切换 / 多局战绩）。

**结果**：就是现在 `game/tests/verify_game.mjs` 的样子——70 项断言，全部通过。

## 5. 防「纯粘贴」：两处关键逻辑，用我自己的话讲

### 5.1 为什么「搜索到一半」会让 AI 变笨？（迭代加深是怎么救回来的）

AI 每个回合要比较四个方向的「期望分」，然后挑最大的那个。

问题出在**时间不够的时候**：搜索是被一个时间预算掐断的，掐断时返回的这个分数
**不是完整搜索的结果**，而是一个「只算了一部分」的残缺值。而且它一定偏小——
因为期望是「求和 ÷ 空格数」，空格还没遍历完就退出了，分子只加了一部分，分母却是完整的。

于是发生了一件很隐蔽的事：假设「向左」这一格刚好把时间用光、被截断，得到 8000 分；
而「向右」完整搜完，得到 9000 分。那么 AI 会认为向右更好——**但这两个数根本不可比**，
一个是残缺值、一个是完整值。真实情况可能是向左本来有 12000 分。
更糟的是这个错误还会被缓存放大（残缺值写进置换表，后面一直读到它）。

修法是**迭代加深**：从 2 层开始，一层一层往下搜：
- 2 层：四个方向都完整搜完 → 记下这一层的结果
- 3 层：四个方向都完整搜完 → 覆盖上一层的结果
- 4 层：搜到一半时间到了 → **整层丢弃**，仍然用 3 层的结果

这样保证「拿来比较的分数永远是同一深度、且四个方向都完整搜索出来的」，
尺度一致，比较才有意义。同时时间也没浪费：局面简单时会自动多搜几层。

### 5.2 为什么评分函数是「角块权重 10/5/2/1」这种形状？

一开始我以为评分函数越「全面」越好，就把空格数、相邻同级对数、单调性、可合并对数
全都加权加起来。结果 AI 一直在原地打转，最高 256。

后来换了个角度想：**2048 里最值钱的资源不是分数，是「合并的顺序」**。
棋盘上真正危险的不是空格少，而是「大块散在中间、每个方向都动不了」。
如果一个 1024 待在角落里，无论往另外三个方向怎么滑，它都还在角落，周围的小块还能继续喂给它；
如果它跑到中间，你随便一动它就被挤走，之后想再凑一个 1024 就几乎不可能了。

所以真正该教的规则是：**大块必须待在角上，并且沿着一条边按从大到小排开**。
「权重 10 / 5 / 2 / 1」这张表就是把这句话翻译成数学：
离角最近的那格权重 10，沿边依次 5、2、1，中间和远端的格子权重是 0（那些位置放什么都不加分）。
四个角各算一次取最大值，等于允许 AI 自己选「这局主要经营哪个角」。

这个改动让 AI 从「最高 256」变成「稳定 1024」。
**教训**：评估函数的形状比项目数量重要得多——要写的是这个游戏的**策略**，
而不是把能想到的指标都堆上去。

## 6. AI 给过但我查证后认为是错误的信息

| AI 的说法 | 我的查证过程 | 结论 |
| --- | --- | --- |
| 「JS 里 `1 << 48` 可以像 C 的 `uint64_t` 那样把棋盘压成一个 64 位整数」 | 我按它的写法实现后，AI 每一步都在走坏棋。于是写脚本把「位棋盘移动结果」和「数组层移动结果」逐格对比，**立刻发现两者不一致**。查 JS 规范：位运算在 32 位有符号整数上进行，移位量会先对 32 取模，`1 << 48` 实际等于 `1 << 16`，**而且不报错** | ❌ 错的。改成 lo/hi 两个 32 位整数，移位一律控制在 32 位内；并在验收脚本里加了「位棋盘与数组层必须逐格一致」的断言，防止以后再犯 |
| 「用 `lo + hi * 2**32` 把两半合成一个整数当缓存键就够了」 | 实测 AI 又变差了。核对 JS 的 `Number.MAX_SAFE_INTEGER = 2^53 - 1`：64 bit 的棋盘远远超出，高位被静默丢弃 —— 也就是说**取出来的根本不是原来那个局面**，等于在缓存里随机撞键 | ❌ 错的。改成拼字符串做键（`lo + ':' + hi`）；搜索热路径上的整数键必须自己保证「各字段位宽不重叠、总和 ≤ 53 bit」，不能想当然地乘上去 |
| 「缓存键要做哈希混合（avalanche）才不容易撞，用 `Math.imul` 混一下更稳」 | 我照做了，然后整局跑得慢到卡死。用 `node --cpu-prof` 抓了 CPU 剖面：`mix32` 占 41%、`keyOfDepth` 再占 10% —— **一半的时间花在算键上**。A/B 对比后换成纯位拼接，搜索快 3.8 倍，1024 达成率 3/6 → 6/6 | ❌ 错的（在这个场景下）。置换表要的是「便宜且基本不撞」，不是抗碰撞的哈希质量；把两次乘法换成一次乘法，收益比任何搜索优化都大 |
| （任务书里给的）Croc 论文编号 `arXiv:2606.25673` | arXiv 编号格式是 `YYMM.NNNNN`，`2606` 表示 2026 年 6 月；用标题关键词检索时对不上，而任务书自己同时给了项目地址 `pulp-platform/croc`，用项目名才找得到正确入口 | ⚠️ 存疑，已按项目名检索为准。**查证过程比结论重要**：先看编号规则、再用标题反查，两条路对不上就不采信编号 |
| 「搜得越深一定越强」 | 用固定种子做 A/B：`depth=3` 能到 1024，`depth=4/5/6` 反而只到 256~512，而且更慢 | ❌ 在**有时间预算**的前提下不成立。原因是截断值污染了比较（见 5.1）。改成迭代加深 + 只认完整层之后，深搜才真正发挥作用 |

## 7. 玩法和实现上的一些细节

- **拖拽/滑动阈值 24 px**，低于这个值当点击处理，避免手一抖就动一步。
- **AI 演示时忽略键盘/鼠标输入**，保证「全程无需人工操作」这条硬指标不被误触破坏。
- **合出 1024 时弹出提示但不强制中断**，可以继续冲 2048；提示层在下一次操作时自动收起。
- **`localStorage` 不可用（隐私模式/被禁用）时自动降级为内存存储**，不会报错白屏。
- **大数字字号自动缩小**，1024 / 2048 不会溢出格子。
- 尊重系统的 `prefers-reduced-motion`：开了「减少动态效果」时关掉方块动画。
